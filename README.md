# CMIP — Climate Autoencoder / Latent-Space Invariance Project

This project studies, using output from the **CESM2 (CMIP6)** climate model, to
what extent **autoencoders** can learn latent representations that (a)
reconstruct/predict climate variables (temperature, precipitation, etc.) and
(b) capture a structure that is **invariant to climate** (historical vs. SSP
scenarios), by comparing several architectures and alignment methods (CERA,
ClimaX, simple/physical baselines...).

This README describes the architecture of the repository (`~/CMIP`), the data
stored in `/glade/work/tsalin/CMIP` and `/glade/derecho/scratch/tsalin/CMIP`,
and gives a summary of every notebook in the `notebooks/` folder.

---

## 1. Pipeline overview

```
CESM2 (CMIP6, intake-esm)
        │  jobs/pipelineNG.py
        ▼
Raw Zarr stores per scenario (scratch: historical/, ssp126/, ssp245/, ssp370/, ssp585/)
        │  jobs/build_multivariate_samples_optimized.py
        ▼
"Patched" multivariate samples (scratch: derived/multivariate_samples_optimized*_v*)
        │  notebooks/trainings/{mask,variable}/*.ipynb  (submitted via jobs/*.pbs)
        ▼
Trained models + latents (work: model_evaluation/, latent_representations/, plots/)
        │  notebooks/analysis/CMIP_analysis_agregate*.ipynb
        ▼
Aggregated tables (model_evaluation/agregate_display/*.pkl, reportGraph/csv/*.csv)
        │  reportGraph/CMIP_reportGraph.ipynb
        ▼
Final summary figures (reportGraph/Graph/*.png)
```

The **experiments** (exp3, exp4, exp5...) correspond to successive
architectures / training protocols, from simplest to most advanced:

| Experiment | Main idea |
|---|---|
| **exp3** | Autoencoder (CNN) trained with increasing climate diversity, several architecture variants (`AEh`, `AEhs2`, `AEhs2s3`, `AEall`). |
| **exp4** | Adds a cross-climate alignment term (`swd` = Sliced-Wasserstein Distance) to the loss, weighted by `LAMBDA_ALIGN`. |
| **exp5** | Final **CERA**-type architecture (autoencoder + prediction head + alignment), compared against several **baselines**: `baseline_simple`, `baseline_physical` (physical formula, no learning), `baseline_ClimaX` (pretrained ClimaX features), `baseline_CERA_noalign` (CERA without the alignment term). Additional variants: `CERA_full_latent` (alignment over all 64 dims instead of 48), `CERA_seasonal` (adds seasonal features). |

Each experiment comes in two task flavors:
- **`variable`**: predict a target climate variable (e.g. `pr`, `tas`) from the latent.
- **`mask`**: predict the value of a masked geographic point in the input patch (reconstruction with masking).

## 2. Repository layout — `~/CMIP`

```
CMIP/
├── README.md                  ← this file
├── jobs/                      ← data-pipeline scripts + PBS/Python wrappers for batch-running notebooks
├── logs/                      ← stdout/stderr of PBS jobs (currently empty / cleared)
├── model_evaluation/          ← local mirror (often empty, see §3) of model outputs; feeds the analysis notebooks
├── notebooks/                 ← the project's "active" notebooks (see §4 and §5)
│   ├── analysis/               → cross-cutting analysis notebooks (distribution, latents, performance, aggregation)
│   └── trainings/
│       ├── mask/                → training notebooks for the masked-point prediction task
│       └── variable/            → training notebooks for the variable prediction task
├── old notebooks/             ← older versions / drafts of the notebooks above (history, unmaintained — see §6)
└── reportGraph/                ← notebook + CSV + PNG for the final report layout
    ├── csv/                     → metrics exported by the analysis notebooks, consumed by CMIP_reportGraph.ipynb
    └── Graph/                   → final PNG figures generated by CMIP_reportGraph.ipynb
```

### `jobs/`
Contains two families of files:
- **Data pipeline** (run once, upstream of any training):
  - `pipelineNG.py`: downloads/extracts CESM2 variables (historical + 4 SSP scenarios) from NCAR's `intake-esm` catalog and writes them to Zarr under `/glade/derecho/scratch/tsalin/CMIP/<scenario>/`.
  - `build_multivariate_samples_optimized.py`: from the Zarr stores, builds multivariate samples per geographic "patch" (features `.npy` + metadata `.csv`) written to `/glade/derecho/scratch/tsalin/CMIP/derived/`.
  - `run_build_multivariate_samples.pbs`: PBS submission for the script above.
- **Batch execution of training/aggregation notebooks**: for every notebook under `notebooks/trainings/**` and `notebooks/analysis/CMIP_analysis_agregate.ipynb`, there is a matching pair `run_<name>.py` (executes the notebook via `nbclient`, overriding hyperparameters, then exports plots/latents/checkpoints) + `run_<name>.pbs` (GPU PBS submission script, with auto-resubmission on failure — walltime/OOM). The file name matches the notebook it runs (e.g. `run_exp5_variable_CERA.py` ↔ `notebooks/trainings/variable/CMIP_variable_exp5_CERA.ipynb`).

### `logs/`
Standard output/error (`.o`/`.e`) of PBS jobs launched from `jobs/*.pbs`. Currently empty (cleaned up) — refills on every submission.

### `model_evaluation/`
Local copy (under `$HOME`) of the model-output tree, mirroring `/glade/work/tsalin/CMIP/model_evaluation/` (see §3). One subfolder per setup: `Baseline_CERA_noalign/`, `Baseline_ClimaX/`, `Baseline_physical/`, `Baseline_simple/`, `CERA/`, `CERA_full_latent/`, `CERA_seasonal/`, `exp3/`, `exp4/`, plus `agregate_display/` (aggregated tables, see §3). Most of these subfolders are **currently empty** under `$HOME` (large checkpoints live on `work`/`scratch`) except for `Baseline_ClimaX/` (pretrained ClimaX weights), `exp4/` (one checkpoint), and `agregate_display/` (`.pkl` tables).

### `notebooks/`
See the full breakdown in §4 and §5.

### `old notebooks/`
Earlier versions, drafts, and debug variants (`_safe`, `_old_df`, `_old_pkl`, `_2004`, etc.) of the notebooks now living in `notebooks/`. Kept for history but **unmaintained** — for any reuse, start from the notebooks in `notebooks/`.

### `reportGraph/`
Last step of the chain: `CMIP_reportGraph.ipynb` reads the metric CSVs (`csv/`, produced by the analysis notebooks — RMSE, R², correlations, climate classification...) and generates the final summary figures (`Graph/*.png`: climate classification maps, RMSE/R² by scenario, latent t-SNE, effective rank, etc.).

## 3. Data on `work` and `scratch`

The `~/CMIP` repository deliberately holds only code and a few small
artifacts; the large datasets live on the shared GLADE filesystems:

### `/glade/derecho/scratch/tsalin/CMIP/` — raw data and derived samples

| Subfolder | Contents | Produced by |
|---|---|---|
| `historical/CESM2_historical_1950_2014.zarr` | CESM2 Zarr, 1950–2014, 16 variables (`tas`, `ta850`, `ta500`, `huss`, `hus850`, `hus500`, `ua850`, `va850`, `ua500`, `va500`, `wap500`, `zg500`, `pr`, `psl`, `rsds`, `sfcWind`) + `lat`/`lon`/`time` coordinates | `jobs/pipelineNG.py` |
| `ssp126/`, `ssp245/`, `ssp370/`, `ssp585/CESM2_ssp<xxx>_2015_2100.zarr` | Same structure, 2015–2100 projections for each SSP scenario | `jobs/pipelineNG.py` |
| `derived/multivariate_samples[_optimized][_NG][_NGS]_v<N>/` | "Patched" samples ready for training: `features_<climate>.npy` (patch tensors), `metadata_<climate>.csv`, `sample_pairs_<climate>.csv`, `patch_catalog.csv`, `run_config.json` (build hyperparameters: `max_abs_lat`, `patch_size_km`, `n_lat`/`n_lon`, selected variables...), `nan_summary_by_variable.csv`, `sampling_diagnostics.csv`. `<N>` = number of samples (`v1` through `v5000000`); `NG`/`NGS` suffixes = build variants (different scenario/variable sets, see the `run_config.json` in each folder) | `jobs/build_multivariate_samples_optimized.py` |
| `combined/` | Currently empty (reserved location) | — |

### `/glade/work/tsalin/CMIP/` — training and notebook outputs

| Subfolder | Contents | Produced by |
|---|---|---|
| `executed_notebooks/` | Executed copies (`*.executed.ipynb`) of the training/mask notebooks, one per run (often suffixed `_run1`, `_runtas`, `_runMLP`...) — a reproducible trace of each run with its outputs | `jobs/run_*.py` (via `nbclient`) |
| `model_evaluation/<Setup>/` | Model checkpoints (`.pt`) and per-run metric tables (`quality_df*.pkl`, `run_manifest.json`) for each setup: `CERA/` (the largest, 246 files — hyperparameter grid explored), `CERA_full_latent/`, `CERA_seasonal/`, `Baseline_CERA_noalign/`, `Baseline_ClimaX/`, `Baseline_physical/`, `Baseline_simple/`, `exp3/`, `exp4/` | notebooks under `notebooks/trainings/variable/` and `mask/`, via `jobs/run_*.py` |
| `latent_representations/latent_representations_exp_{3,4,5}/` | Latent representations computed on the test set (`*_latent_representations_df.pkl`) for each combination (architecture, variable, hyperparameters) + `*_run_manifest.json` — this is the data consumed by the `CMIP_analysis_latent*.ipynb` notebooks | same as above |
| `plots/plots_exp_{3,4,5}/` | PNG figures automatically exported from the training notebooks (loss curves, reconstructions, etc.) | same as above |

**Note (see project memory):** t-SNE / latent visualizations for the
`ClimaX` and `exp3` setups still need to be generated (the corresponding
`_latent_representations_df.pkl` files exist but are not yet consumed by
every `analysis` notebook).

### How the notebooks reference these paths
The notebooks don't hard-code these paths everywhere by hand: most expose a
configuration cell at the top (`PROJECT_DIR`, `WORK_DIR`, `SCRATCH_DIR`,
`NUM_SAMPLE`, etc.) that points to the folders above; these are the same
variables that the `jobs/run_*.py` scripts override when running a notebook
in batch mode with different hyperparameters.

## 4. Training notebooks — `notebooks/trainings/`

Each notebook can be run interactively or submitted in batch mode via the
matching `.pbs` file in `jobs/` (the `qsub` command is given at the top of
each notebook). All variants apply the same rigorous protocol: train/val/test
split performed before standardization, normalization statistics fitted only
on the training set, masked points excluded from that fit.

### `trainings/mask/` — masked-point prediction task

| Notebook | Description |
|---|---|
| `CMIP_mask_exp3.ipynb` | exp3 baseline: CNN autoencoder, several variants (`AEh`, `AEhs2`, `AEhs2s3`, `AEall`), no cross-climate alignment term. |
| `CMIP_mask_exp4.ipynb` | Same as exp3 + a Sliced-Wasserstein alignment term (`swd`) between climates, weighted by `LAMBDA_ALIGN`. |
| `CMIP_mask_exp5_baseline_simple.ipynb` | "Simple" baseline (no alignment, minimal architecture) for the masked task. |
| `CMIP_mask_exp5_baseline_CERA_noalign.ipynb` | Full CERA architecture but **without** the alignment term — control baseline to isolate the effect of alignment. |
| `CMIP_mask_exp5_CERA.ipynb` | Full CERA architecture (autoencoder + `swd` alignment) for the masked task. |

### `trainings/variable/` — climate variable prediction task

| Notebook | Description |
|---|---|
| `CMIP_variable_exp3.ipynb` | exp3 baseline for variable prediction (e.g. `pr`, `tas`) from the latent. |
| `CMIP_variable_exp4.ipynb` | Same as exp3 + `swd` alignment (`LAMBDA_ALIGN`). |
| `CMIP_variable_exp5_baseline_simple.ipynb` | Simple baseline, variable task. |
| `CMIP_variable_exp5_baseline_physical_pr.ipynb` | "Physical" baseline: a physical formula/heuristic (no learning) to predict `pr`. |
| `CMIP_variable_exp5_baseline_physical_tas.ipynb` | Same, for `tas`. |
| `CMIP_variable_exp5_baseline_CERA_noalign.ipynb` | Full CERA without alignment, variable task (control). |
| `CMIP_variable_exp5_baseline_ClimaX.ipynb` | Baseline using features from the pretrained **ClimaX** model (`model_evaluation/Baseline_ClimaX/climax_pretrained.ckpt`) as input to the prediction head. |
| `CMIP_variable_exp5_baseline_ClimaX_enhanced.ipynb` | Variant of the ClimaX baseline enriched with seasonal features (`sin`/`cos` of the month) concatenated to the 64D latent before the prediction head. |
| `CMIP_variable_exp5_CERA.ipynb` | Full CERA architecture, alignment over 48 of the 64 latent dimensions. |
| `CMIP_variable_exp5_CERA_full_latent.ipynb` | CERA variant where alignment covers the **full 64 dimensions** of the latent (instead of 48). |
| `CMIP_variable_exp5_CERA_seasonal.ipynb` | CERA variant with additional seasonal features. |

## 5. Analysis notebooks — `notebooks/analysis/`

These notebooks consume the training outputs (`latent_representations/`,
`model_evaluation/*/quality_df*.pkl`) and/or the derived samples
(`derived/multivariate_samples*`) to produce comparative diagnostics across
setups.

| Notebook | Description |
|---|---|
| `CMIP_analysis_distribution.ipynb` | Multivariate analysis of the distribution shift between climates (historical vs. SSP), from the raw sampled patches. |
| `CMIP_analysis_distribution_onevariable.ipynb` | Same analysis but per variable (univariate), from the same precomputed samples. |
| `CMIP_analysis_latent.ipynb` | Study of the latent representations learned by the autoencoders (exp3 and later): structure, separability by climate, etc. |
| `CMIP_analysis_latent_vizualisations.ipynb` | Dedicated latent visualizations (t-SNE, projections) for the same experiments. |
| `CMIP_analysis_latent_invariant.ipynb` | Uses a generalized eigenvalue decomposition to find the latent direction(s) that best encode a climate-invariant structure (physically corresponding pairs across climates). |
| `CMIP_analysis_latent_ratio.ipynb` | Follow-up diagnostic to `latent_invariant`: computes whether the cross-climate physical structure is spread across the whole latent space or concentrated in just a few directions (compared to a nearest-neighbor "raw data" baseline). |
| `CMIP_analysis_mask_performance.ipynb` | Reconstruction/prediction performance for the masked-point task (exp3 and later), compared across setups. |
| `CMIP_analysis_variable_performance.ipynb` | Variable-prediction performance (RMSE, R²...) compared across setups, for a given hyperparameter configuration. |
| `CMIP_analysis_variable_hyperparameters.ipynb` | Sensitivity study to hyperparameters (e.g. `LAMBDA_ALIGN`, `LAMBDA_PRED`, sample size) for the variable prediction task. |
| `CMIP_analysis_agregate.ipynb` | For a fixed set of 7 architectures (one hyperparameter configuration each), combines the four analyses above into a single tidy DataFrame (one row per setup): R² per SSP scenario, climate-classifier accuracy (invariance proxy), and the `latent_invariant`/`latent_ratio` diagnostics. Saves the result to `model_evaluation/agregate_display/` and `reportGraph/csv/`. Can be run in batch mode via `jobs/run_agregate.py`. |
| `CMIP_analysis_agregate_display.ipynb` | Reads and formats (filters by hyperparameters/setups) the tables produced by `CMIP_analysis_agregate.ipynb`. |

## 6. `old notebooks/` and `reportGraph/`

- **`old notebooks/`**: archive of earlier versions of the notebooks above
  (suffixes `_safe`, `_safe_2`, `_old_pkl`, `_old_df`,
  `_preprocessing_corrected`, dates like `_1604`/`_2004`...). Useful for
  tracing the history of a preprocessing choice, but **not meant to be reused
  as a starting point** — the active notebooks in `notebooks/` reflect the
  current, rigorous protocol.
- **`reportGraph/CMIP_reportGraph.ipynb`**: final notebook that reads the
  aggregated CSVs (`reportGraph/csv/`, themselves produced in part by
  `CMIP_analysis_agregate.ipynb` and other analysis notebooks — global/extreme
  RMSE, ratio vs. historical, correlations, reconstruction summary table) and
  produces all the report's summary figures (`reportGraph/Graph/*.png`:
  climate classification, RMSE/R² by variable and scenario, t-SNE, latent
  effective rank, per-setup SR (self-recovery?) outputs, etc.).

## 7. Picking the project back up

1. The raw CESM2 data is already on `scratch` (`historical/`, `ssp*/`) — no
   need to re-run `pipelineNG.py` unless you're adding a scenario or a
   variable.
2. Derived samples already exist at several sizes (`derived/`) — check the
   `run_config.json` in each folder for the exact build hyperparameters
   before reusing one.
3. To train a new setup: start from the closest notebook in
   `trainings/variable/` or `trainings/mask/`, adjust the hyperparameters at
   the top of the notebook, then submit via the matching `.pbs` file in
   `jobs/` (or duplicate the `.py`/`.pbs` pair for a new setup).
4. To compare a new setup against the others: make sure it writes its
   `quality_df*.pkl` / `*_latent_representations_df.pkl` in the same format
   as the existing setups, add it to the "Setups compared" table in
   `CMIP_analysis_agregate.ipynb`, then re-run the aggregation.
